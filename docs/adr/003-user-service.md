# ADR-003: User Service и управление JWT-сессиями

- Статус: принято
- Дата: 2026-10-15

## Контекст

OpenAPI-контракт маркетплейса требует регистрацию, вход и обновление токенов. Commerce Service уже проверяет access JWT и использует содержащиеся в нём идентификатор пользователя и роль, но не владеет учётными данными и не выпускает токены.

Данные пользователей должны принадлежать отдельному User Service и храниться в отдельной PostgreSQL-базе. Commerce Service получает сведения о пользователе только из подписанного access JWT и не обращается в User DB.

## Рассмотренные варианты refresh-токена

### Полностью stateless JWT

Refresh JWT можно проверять только по подписи и сроку действия, ничего не сохраняя в базе.

Преимущества: простая реализация и отсутствие обращения к базе при обновлении токена. Недостатки: украденный refresh-токен нельзя отозвать до окончания его срока действия, а повторное использование невозможно обнаружить.

### Случайный opaque-токен

Клиент получает случайную строку, хеш которой хранится в базе.

Преимущества: простой отзыв и отсутствие данных пользователя внутри токена. Недостаток для этого задания — требование двух типов JWT-токенов выполняется менее явно.

### JWT с серверной сессией и ротацией

Refresh-токен является JWT, но его SHA-256-хеш хранится в User DB. При успешном обновлении старая запись атомарно заменяется новой.

Преимущества: сохраняется единый формат JWT, токен можно отозвать, а повторное использование старого refresh-токена отклоняется. Недостатки: обновление токена зависит от User DB и требует дополнительной таблицы.

## Решение

Выбран JWT с серверной сессией и обязательной ротацией refresh-токена.

User Service реализуется отдельным Go-модулем со слоями:

```text
HTTP request → handler → service → repository → User DB
```

- `handler` использует сгенерированные из OpenAPI маршруты и DTO, выполняет контрактную валидацию и преобразует ошибки в HTTP-ответы;
- `service` нормализует email, хеширует и проверяет пароль, выпускает токены и управляет ротацией refresh-сессий;
- `repository` выполняет запросы к PostgreSQL и не принимает бизнес-решений.

Код User API генерируется из общего `api/openapi.yaml` по тегам `System` и `Auth`. Ручные HTTP DTO не создаются.

## User DB

User Service владеет двумя таблицами.

### `users`

| Поле | Тип | Назначение |
|---|---|---|
| `id` | UUID | Идентификатор пользователя |
| `email` | VARCHAR(254) | Нормализованный уникальный email |
| `password_hash` | VARCHAR(60) | bcrypt-хеш пароля |
| `role` | ENUM | `USER`, `SELLER` или `ADMIN` |
| `created_at` | TIMESTAMPTZ | Время создания |
| `updated_at` | TIMESTAMPTZ | Время изменения |

Email перед сохранением приводится к нижнему регистру и очищается от пробелов по краям. В базе дополнительно действует ограничение `email = lower(email)` и уникальный индекс.

### `refresh_tokens`

| Поле | Тип | Назначение |
|---|---|---|
| `id` | UUID | Идентификатор refresh-сессии и claim `jti` |
| `user_id` | UUID | Владелец сессии |
| `token_hash` | BYTEA | SHA-256-хеш полного JWT |
| `expires_at` | TIMESTAMPTZ | Срок действия |
| `created_at` | TIMESTAMPTZ | Время создания |

Полный refresh-токен в базе не хранится. При удалении пользователя его refresh-сессии удаляются каскадно.

Схема создаётся Flyway-миграцией. User Service не имеет доступа к Commerce DB, а `user_id` и `seller_id` в Commerce DB остаются внешними идентификаторами без межбазовых внешних ключей.

## Регистрация и роли

`POST /auth/register` принимает только роли `USER` и `SELLER`, как указано в OpenAPI. Пароль хешируется bcrypt до записи в базу. Повторный нормализованный email возвращает `EMAIL_ALREADY_EXISTS` и статус `409`.

Публично зарегистрировать `ADMIN` нельзя. Для локального и демонстрационного окружения User Service идемпотентно создаёт администратора при старте, если заданы `ADMIN_EMAIL` и `ADMIN_PASSWORD`. Повторный запуск не создаёт дубликат и не меняет существующую учётную запись.

## Access JWT

Access-токен подписывается HS256 и по умолчанию действует 20 минут. Он содержит:

- `sub` — UUID пользователя;
- `role` — `USER`, `SELLER` или `ADMIN`;
- `token_type` — `access`;
- `iss`, `iat`, `exp` — стандартные claims.

`JWT_SECRET` и `JWT_ISSUER` совпадают в User Service и Commerce Service. Commerce Service проверяет подпись, issuer, срок действия, роль и `token_type=access` без синхронного обращения к User Service.

## Refresh JWT

Refresh-токен подписывается тем же алгоритмом и по умолчанию действует 14 дней. Он содержит:

- `sub` — UUID пользователя;
- `role` — роль на момент выпуска;
- `token_type` — `refresh`;
- `jti` — UUID записи в `refresh_tokens`;
- `iss`, `iat`, `exp` — стандартные claims.

При `POST /auth/refresh` User Service:

1. Проверяет подпись, issuer, срок действия и `token_type=refresh`.
2. Вычисляет SHA-256-хеш переданного токена.
3. Создаёт новую пару access/refresh JWT.
4. В одной транзакции блокирует старую refresh-сессию, сверяет `jti`, пользователя, хеш и срок действия, затем заменяет её новой сессией.
5. Возвращает новую пару токенов.

Повторное использование старого refresh-токена возвращает `REFRESH_TOKEN_INVALID` со статусом `401`.

## Вход и ошибки

`POST /auth/login` ищет пользователя по нормализованному email и сравнивает bcrypt-хеш. Несуществующий email и неверный пароль возвращают одинаковую ошибку `INVALID_CREDENTIALS`, чтобы не раскрывать наличие учётной записи.

Ошибки User Service не содержат HTTP-статус в слое `service`. Преобразование выполняет `handler`:

| Код | HTTP-статус |
|---|---|
| `VALIDATION_ERROR` | 400 |
| `INVALID_CREDENTIALS` | 401 |
| `REFRESH_TOKEN_INVALID` | 401 |
| `EMAIL_ALREADY_EXISTS` | 409 |
| `INTERNAL_ERROR` | 500 |

Ответ соответствует общей схеме `ErrorResponse` из OpenAPI.

## Логирование и чувствительные данные

User Service логирует каждый запрос в JSON с теми же обязательными полями, что и Commerce Service. В телах запросов маскируются `password`, `access_token`, `refresh_token` и поля, содержащие `secret` или `token`.

В логи не выводятся пароли, JWT, их хеши и `JWT_SECRET`.

## Конфигурация

User Service получает настройки из переменных окружения:

| Переменная | Значение по умолчанию |
|---|---|
| `PORT` | `8081` |
| `DATABASE_URL` | локальная User DB |
| `JWT_SECRET` | общий локальный секрет проекта |
| `JWT_ISSUER` | `marketplace-user-service` |
| `ACCESS_TOKEN_TTL` | `20m` |
| `REFRESH_TOKEN_TTL` | `336h` |
| `ADMIN_EMAIL` | не задан |
| `ADMIN_PASSWORD` | не задан |

Если задана только одна из двух переменных администратора, сервис завершает запуск с ошибкой конфигурации.

## Docker Compose

В Compose добавляются отдельные контейнеры:

- `user-db` — PostgreSQL User Service;
- `user-migrations` — Flyway для User DB;
- `user-service` — HTTP API регистрации и токенов.

User Service запускается только после успешного применения миграций. API Gateway и единый внешний порт добавляются отдельным следующим этапом после готовности обоих сервисов.

## Проверка

Автоматические тестовые файлы в рамках текущей работы не добавляются. Перед передачей на ревью выполняются:

- воспроизводимая кодогенерация;
- `go build ./...`;
- `go vet ./...`;
- проверка форматирования;
- ручной E2E после подключения Compose: регистрация, вход, refresh с ротацией, повторное использование старого refresh-токена и авторизованный запрос в Commerce Service.

## Последствия

- User Service становится единственным владельцем учётных данных и refresh-сессий;
- Commerce Service остаётся независимым от доступности User Service при проверке access JWT;
- обновление refresh-токена требует доступной User DB;
- в текущем API роль пользователя не изменяется; refresh-токен переносит в новую пару роль из подписанного токена;
- компрометация общего HMAC-секрета позволяет выпускать токены от имени User Service, поэтому для production-подобного окружения предпочтительна асимметричная подпись, но она не входит в scope учебного задания.
