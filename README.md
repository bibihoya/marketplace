# Маркетплейс

Сейчас в проекте есть описание архитектуры маркетплейса, C4-диаграмма и запускаемая версия (заглушка) одного из микросервисов — Catalog Service.

Цель проекта — написать свой учебный маркетплейс и постепенно добавлять в него новые части в следующих домашних заданиях.

В Catalog Service пока нет бизнес-логики: он нужен, чтобы проверить сборку, запуск в Docker и работу `GET /health`. Остальные сервисы показаны только как части будущей системы.

## Что входит в проект

Архитектура покрывает функции из задания:

- персонализированную ленту товаров;
- управление товарным каталогом для продавцов;
- управление пользователями с ролями покупателя и продавца;
- оформление заказов;
- расчёт и учёт платежей;
- уведомления о статусах заказов.

Доставка, складские остатки, отзывы, скидки, промокоды и административная панель пока не рассматриваются. Доставку при необходимости можно добавить позже отдельным сервисом.

## Домены и сервисы

| Домен | Сервис | За что отвечает |
|---|---|---|
| Пользователи | User Service | Регистрация, вход, общий профиль, роли и состояние учётной записи |
| Каталог | Catalog Service | Создание и изменение товаров, категории, цены и публикация товаров |
| Лента и персонализация | Feed Service | Просмотры, предпочтения, популярность товаров и порядок выдачи |
| Заказы | Order Service | Оформление заказа, его состав, итоговая стоимость и статусы |
| Платежи | Payment Service | Создание платежа, обращение к платёжному провайдеру и учёт результата |
| Уведомления | Notification Service | Отправка уведомлений при изменении статуса заказа |

Покупатель и продавец — это роли одной учётной записи в User Service. Отдельные сервисы профилей здесь не нужны: продавец работает с товарами через Catalog Service, а покупатель — с лентой и заказами через Feed Service и Order Service.

## Как работает персонализация

- новый или неавторизованный пользователь видит популярные опубликованные товары;
- для авторизованного пользователя выше показываются категории, которые он чаще смотрит и покупает;
- Feed Service получает изменения каталога и информацию об оплаченных заказах через события;
- у Feed Service есть своя копия данных, необходимых для построения ленты;
- исходные карточки товаров и цены по-прежнему хранятся в Catalog Service.

## Кто какими данными владеет

В целевой архитектуре у каждого сервиса своя база PostgreSQL. Сервисы не используют общие таблицы и не обращаются напрямую к чужим базам.

| Сервис | Какие данные хранит |
|---|---|
| User Service | Пользователи, данные для входа, роли, контакты и состояние учётной записи |
| Catalog Service | Товары, категории, актуальные цены и статусы публикации |
| Feed Service | Просмотры, предпочтения, популярность и копию опубликованных товаров для ленты |
| Order Service | Заказы, позиции, сохранённые на момент заказа названия и цены, итоговую сумму и статусы |
| Payment Service | Платежи, попытки оплаты, идентификаторы внешних транзакций и их статусы |
| Notification Service | Шаблоны, попытки отправки и результаты доставки уведомлений |

Копия товаров в Feed Service нужна только для быстрой выдачи. Она не заменяет данные Catalog Service. По той же причине Order Service сохраняет название и цену товара на момент оформления заказа: последующее изменение карточки не должно менять старый заказ.

## Как сервисы взаимодействуют

HTTP используется, когда ответ нужен сразу. RabbitMQ используется для событий, которые можно обработать асинхронно.

| Откуда | Куда | Как | Для чего |
|---|---|---|---|
| Web Application | API Gateway | HTTPS, синхронно | Все запросы покупателя и продавца |
| API Gateway | User Service | HTTP, синхронно | Работа с учётной записью и профилем |
| API Gateway | Catalog Service | HTTP, синхронно | Просмотр и управление товарами |
| API Gateway | Feed Service | HTTP, синхронно | Получение ленты и запись просмотров |
| API Gateway | Order Service | HTTP, синхронно | Оформление и просмотр заказов |
| Order Service | Catalog Service | HTTP, синхронно | Получение актуальных товаров и цен |
| Catalog Service | Feed Service | RabbitMQ, асинхронно | Обновление товаров в ленте |
| Order Service | Payment Service | RabbitMQ, асинхронно | Создание платежа после оформления заказа |
| Payment Service | Order Service | RabbitMQ, асинхронно | Передача результата оплаты |
| Order Service | Feed Service | RabbitMQ, асинхронно | Учёт оплаченной покупки в предпочтениях |
| Order Service | Notification Service | RabbitMQ, асинхронно | Отправка уведомления после изменения статуса заказа |
| Notification Service | User Service | HTTP, синхронно | Получение актуального контакта пользователя |
| Payment Service | Payment Provider | HTTPS, синхронно | Проведение платежа |
| Notification Service | Notification Provider | HTTPS, синхронно | Отправка сообщения пользователю |

Сообщение из RabbitMQ может прийти повторно, поэтому сервисы должны уметь безопасно обработать его ещё раз.

## Как оформляется заказ

1. Order Service получает состав заказа.
2. Запрашивает в Catalog Service актуальные товары и цены.
3. Сохраняет состав заказа и цены на момент оформления.
4. Публикует событие `OrderCreated`.
5. Payment Service создаёт платёж на сумму заказа и обращается к внешнему провайдеру.
6. Результат оплаты возвращается событием `PaymentSucceeded` или `PaymentFailed`.
7. Order Service меняет статус заказа и публикует `OrderStatusChanged`.
8. Notification Service отправляет уведомление, а Feed Service учитывает оплаченную покупку при построении ленты.

Сейчас сумма платежа равна итоговой сумме заказа, потому что доставки, скидок и комиссий в проекте нет.

## Рассмотренные варианты

### Модульный монолит

Все домены можно было бы собрать в одном приложении и использовать одну базу данных.

Плюсы:

- проще запустить и развернуть;
- меньше инфраструктуры;
- проще выполнять операции, которые затрагивают несколько модулей;
- дешевле поддерживать на старте.

Минусы:

- все части приложения разворачиваются и масштабируются вместе;
- ошибка в одном модуле может затронуть всё приложение;
- границы между доменами со временем проще нарушить.

### Микросервисы

Каждый домен можно вынести в отдельный сервис со своей базой, а для обмена использовать HTTP и события.

Плюсы:

- понятные границы ответственности;
- каждый сервис сам владеет своими данными;
- сервисы можно выпускать и масштабировать отдельно;
- обработка платежа и отправка уведомления не блокируют основной запрос.

Минусы:

- сложнее запуск и поддержка всей системы;
- нельзя сделать одну транзакцию сразу для нескольких сервисов;
- данные в разных сервисах обновляются не одновременно;
- нужно обрабатывать повторы и сбои при доставке событий.

### Почему выбраны микросервисы

Для этой работы выбран вариант с микросервисами. Он лучше показывает границы доменов, владение данными и синхронные и асинхронные взаимодействия — именно это требуется в задании. Для небольшой учебной реализации модульный монолит был бы проще, но хуже продемонстрировал бы эти архитектурные решения.

Более формальная запись решения находится в [`docs/adr/001-service-decomposition.md`](docs/adr/001-service-decomposition.md).

## Что реализовано

Реализован только Catalog Service без бизнес-логики. У него есть один адрес для проверки работоспособности:

```http
GET /health HTTP/1.1
Host: localhost:8080
```

Ответ:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"status":"ok","service":"catalog-service"}
```

## Как запустить

### В Docker

Нужны Docker Engine или совместимая среда, например Colima, и Docker Compose v2.

```bash
docker compose up --build -d
```

Проверить контейнер и health-check:

```bash
docker compose ps
curl -i http://localhost:8080/health
```

Остановить контейнер:

```bash
docker compose down
```

### Без Docker

Понадобится Go 1.26 или новее.

```bash
cd services/catalog-service
go run ./cmd/server
```

После запуска в другом терминале:

```bash
curl -i http://localhost:8080/health
```
